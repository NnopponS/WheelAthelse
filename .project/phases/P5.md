# P5 conclusion: Windows time-window review and export

## Outcome

**Windows source workflow implemented and verified. No installed binary was updated or released.** The frozen legacy XY+yaw recipe remains first/default. An explicit **Experimental PyTorch Residual v1** option and a read-only research-trial browser are now available in source for local comparison; neither changes production current_best. This is software/research tooling delivery, not independent trajectory-accuracy acceptance.

## User workflow

Open a finalized recording from Results and enter MODEL. Confirm recording and model identity, then run offline analysis. The full trajectory remains visible with equal X/Y scale. Move the native time slider or keyboard cursor to select an original full-resolution sample. The corresponding XY point and time-series cursor update together. Set start/end times for a window; the highlighted trajectory interval and descriptive statistics refer to the same full-session result.

The review exposes signed forward speed, speed magnitude, longitudinal acceleration, unwrapped yaw and yaw rate when the selected model provides them. It also exposes the separately labeled change in speed magnitude and quality/availability information. A missing value is shown as unavailable, never as an invented zero. Model/recording provenance and warnings remain available in the details view.

Export asks for a parent directory and creates a unique child bundle. `timeline.csv` contains every original model point, not just the selected window or a decimated display. `metadata.json` records model/time/QC provenance, CSV hash and selected-window indices/statistics. `COMPLETE` is written last. Existing raw recordings and earlier exports are not replaced.

## Code changes

`analysis_timeline.py` supplies the Qt timeline, channel plot, selected-point detail, window controls/statistics and export coordination. `analysis_export.py` implements the create-only bundle. `main_window.py::ModelPage` retains the existing recording/model controls and adds the timeline in a scrollable split layout with trajectory cursor/window highlights.

The inference adapter's additional P4 envelope carries the full arrays and identities. It preserves applied zero delay correctly. The controller uses read-only finalized loading. No acquisition daemon or BLE ownership logic was moved into the review widget. Analysis remains asynchronous with selection-generation checks; changing a session/model or closing the view cannot install a stale result as the current selection. Export takes a result snapshot and does not mutate its source recording.

Rendering can decimate a long curve, but source arrays determine bounds, cursor lookup, window summaries and export. Statistics do not rerun the model, refit acceleration or restart pose at the selected window.

### Direct research-trial review

`Research trial…` opens only processed `.npz` files located inside this checkout's `BiWheel3D/data` tree. This boundary is deliberate because the research NPZ schema uses trusted local metadata. The selected model runs directly on the stored `(T,5,12)` SI windows and retains the processed model-step timestamps. The source file and model are hashed and checked for mutation during analysis.

When a processed trial has real C3D GT, the MODEL chart overlays the initial-heading C3D path as a gray dashed trace. The displayed ATE/endpoint/heading values are explicitly labeled **full-cache diagnostics**; model-selection claims must still use the support masks and scoring protocol from the research evaluator. IMU-only trials do not receive fabricated GT. This allows the user to inspect `BiWheel3D/data` from the Python app without converting research caches to `.waj`.

`.pt/.pth` discovery is supported only for the `torch_residual_v1` experimental contract. The local model library currently has an identical copy of the selected checkpoint under `Documents/WheelAthlete/Model/WheelAthlete-PyTorch-Residual-v1.pt`; the source checkpoint and copy both hash to `d838e98e94d5db2e490bf64816e78a35b367ab2d079a54c9d192848973138a45`. PyTorch remains an optional local research dependency rather than a new lean-app/package requirement.
