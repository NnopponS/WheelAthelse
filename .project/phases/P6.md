# P6 conclusion: mobile review/export plus optional center acquisition

Updated: 2026-09-08.

## Outcome

**Mobile source workflow is complete for the existing M4 model and now also supports L/R/C acquisition/storage/export. No center-aware or PyTorch residual estimator is enabled on-device.**

The existing M4 ONNX graph remains the mobile default and runs locally without a PC server.

## Analysis semantics

The mobile review uses the same full-session principles as Windows:
- one stored result,
- exact source-sample cursor,
- inclusive original-sample window selection,
- full-resolution statistics/export,
- unavailable quantities stay unavailable,
- chart rendering does not redefine the data.

For current M4:
- XY is predicted,
- XY-derived speed magnitude/change may be shown when supported,
- chair yaw/yaw-rate are unavailable,
- signed forward speed is unavailable,
- signed longitudinal acceleration is unavailable.

Do not infer chair yaw from path tangent.

## Async/runtime behavior

Preprocessing/inference/export work is kept away from the UI isolate where practical. Provider generation/mounted guards prevent stale async results from replacing a newer selection. Long export encoding/hashing is performed outside the UI-critical path.

## Optional center role in Flutter

`WheelSide.center` / C is now a first-class optional acquisition role rather than falling through a two-value ternary as R.

Current support includes:
- BLE role parsing (`0x43 -> C`),
- connection state/card,
- live IMU state/preview,
- clock/sync state,
- countdown/recording,
- saved session metadata,
- raw CSV parser/export,
- XLSX/ZIP export,
- session preview/filtering,
- quality/session statistics where role-aware.

Current session metadata schema records the center role and axis contract when applicable. Existing old sessions remain readable.

`center_raw.csv` is created **only** when C was recorded. Historical/training CSV remains L/R-only so downstream training code cannot silently reinterpret an old 12-channel schema as 18-channel data.

## Legacy-model isolation

Mobile trajectory preprocessing deliberately selects L/R only. Regression tests insert arbitrarily large C values and verify that the legacy model input is unchanged exactly. This is a contractual guard against accidental enum-expansion contamination.

A future 3-IMU estimator must declare a new explicit feature/input version rather than inheriting the existing M4 or L/R residual contract.

## Residual/Slalom bridge status

Development bundles/fixtures exist for future residual/Slalom parity work, including recording-free course fixtures. This does **not** mean residual v1, course v1 or calibrated course v3 runs in the production mobile app today.

Before any such port:
1. freeze/accept the estimator through P3,
2. reproduce exact feature/baseline/integration math in Dart/ONNX as applicable,
3. create numerical goldens,
4. run Android/iOS native acceptance separately.

## Verification

Latest current working-tree result:
- **715/715 Flutter tests passed**,
- `flutter analyze` reports **No issues found**.

The test set includes new center role/storage/export/recording regressions plus existing model/UI behavior. End-to-end fake BLE recording demonstrated L/R/C save/readback with center metadata, and export demonstrated conditional `center_raw.csv` creation.

These are host/source tests, not a physical phone/three-board RF acceptance.

## What remains

- physical Android/iOS launch/inference/file-picker/BLE acceptance,
- real simultaneous L/R/C capture,
- actual center range/axis/build verification,
- accepted center-aware model,
- coach acceptance.

## P6 conclusion

Mobile is ready to **collect and preserve** the optional center stream without changing the existing model. That is the correct current boundary: data plumbing first, then center-aware modeling only after synchronized reference data exists.
