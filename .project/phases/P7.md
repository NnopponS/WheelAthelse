# P7 physical capture and acceptance protocol

Updated: 2026-09-08.

## Current status

**Source preparation is ready for L/R plus optional C. The XIAO center was flashed with the green `C` identity earlier and visually confirmed by the user, but the final 1.8.1 artifact still needs re-flash/readback plus static +Z-down gravity acceptance because the board disconnected before the version-bumped flash. No new synchronized L/R/C+C3D athlete capture or coach sign-off exists.**

This phase is the work order that converts source support into measured evidence.

## Sensor configuration

Baseline sensors:
- L wheel-hub IMU,
- R wheel-hub IMU.

Optional new instrumentation authorized by the user at source level:
- C chair-center/frame IMU (`0x43`),
- mounting contract: **+Z down toward floor**,
- X/Y remain unmapped board axes until physically documented.

A third IMU is not an absolute position reference. It must be evaluated against the two-hub baseline, not assumed beneficial.

## P7A - Center firmware/bench acceptance

Physical flashing is a separate action and should occur only when the user explicitly requests it.

For the intended center board:
1. record target (XIAO or M5), exact firmware artifact SHA-256 and source checkout state,
2. flash only the center target,
3. verify BLE role/name identifies C rather than L/R,
4. read actual firmware/range/sample-rate/conversion-scale identity back through the app,
5. mount +Z down and hold the chair/board static,
6. verify the expected gravity direction/sign and approximately 1 g magnitude after declared scale conversion,
7. physically mark/document which board axis is chair-forward and chair-lateral,
8. verify green center identity behavior does not mask error/retry indicators,
9. connect L/R/C simultaneously and inspect sequence counters, drop/replay/fault state, queue behavior and start acknowledgements,
10. preserve pre/post clock observations and START mapping for all three streams,
11. save/reopen/export a short L/R/C session and verify C remains C in journal/schema/export.

Do not call this an accuracy test. It is hardware identity/orientation/timing/data-integrity acceptance.

## P7B - Optical reference requirements

The reference must contain actual moving trajectories. For each C3D/reference file verify:
- intended moving markers are present,
- marker-to-wheel/chair mapping is documented,
- units and sample rate are known,
- residual/validity fields are checked,
- dropout runs are visible,
- complete maneuver is retained,
- pairing to IMU capture is independently justified,
- common event/time transform connects reference clock to L/R/C clocks.

The audited 2026-09-05 dynamic C3Ds with `POINT.USED=0` do not satisfy this. Model-derived pseudo markers must never become labels/scores.

## P7C - Capture matrix

For each fixed mounting/remount group collect:
- static before motion,
- forward acceleration / coast / braking,
- reverse,
- one-wheel arc left and right,
- in-place pivot left and right,
- complete Slalom,
- 10x5/shuttle with exact performed turn count/course,
- pause/restart,
- hard braking/turning where slip is plausible.

Repeat across days/remounts and multiple athletes/load/surface conditions as feasible. Keep all windows from one correlated trial/group together.

Log:
- chair/load/tire state/surface,
- measured or inherited geometry status,
- L/R/C physical mount diagram,
- actual firmware artifact and ranges/scales for each sensor,
- configured rate,
- all sequence/drop/replay/FIFO/transport faults,
- clock evidence,
- reference QA,
- operator/reviewer.

Failed captures are retained with reasons; do not delete failures to improve coverage.

## Split/freeze rules

Before examining candidate outcomes, assign each capture group one role:
- development/calibration,
- validation,
- final locked.

Keep participant/day/session/remount together. Historical July `_05` records are not a new final set. Do not tune normalization, delay, geometry, calibration or model selection using the locked final data.

## Two-IMU vs three-IMU study

After capture QA passes:
1. freeze the L/R baseline and its source/config hashes,
2. define an explicit center-aware model feature/input contract,
3. train using development groups only,
4. compare L/R and L/R/C on the **same validation trials**,
5. report per-maneuver changes and regressions,
6. decide whether C actually improves yaw waveform/slip/braking behavior,
7. freeze one candidate,
8. run the final group once.

Do not assume direct raw 18-channel concatenation is optimal. Test physically meaningful uses of C, such as chassis yaw, left/right-vs-center disagreement, braking acceleration or slip/QC features, only when supported by data.

## Evaluation package

For every intended trial report:
- inclusion/exclusion reason,
- reference/timing provenance,
- initial-pose aligned XY trajectory,
- endpoint/path-length/ATE/RPE,
- wrapped and unwrapped heading,
- signed speed,
- yaw rate,
- turn-event timing,
- acceleration using a declared common bandwidth,
- coverage/failures,
- L/R vs L/R/C paired difference.

Protocol-specific constrained estimators require separate raw and constrained metrics. A Slalom closure endpoint near zero cannot be the only score.

## Athlete/coach workflow acceptance

On separately authorized installed builds:
- open a real finalized recording,
- verify athlete/trial/model/quality identity,
- scrub a time and locate the exact path point,
- select a window and inspect speed/braking/turn quantities,
- compare repeats,
- verify missing values are understandable,
- export full-resolution data and validate metadata/hash/COMPLETE,
- reopen the source recording and verify it was not mutated.

Coach thresholds must be agreed **before** final locked evaluation.
