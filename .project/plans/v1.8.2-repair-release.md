# WheelAthlete 1.8.2 repair and release plan

Maintained execution plan. Created 2026-09-09.

## Goal and release boundary

Deliver WheelAthlete 1.8.2 as a Windows-first release that installs, upgrades,
runs, and uninstalls predictably; preserves recordings and custom models; makes
recording selection and model loading clear; and records measured evidence for
the XIAO center-board failure reported after approximately ten minutes.

Keep Flutter source in the repository, label it under maintenance, and publish
no mobile download for 1.8.2. Do not promote a research estimator or change the
existing production model defaults. Do not publish private recordings, local
paths, signing credentials, generated research artifacts, or the separate
`BiWheel3D/` repository.

The release is complete only when every required software gate below passes.
Windows Application Control compatibility remains an external signing gate: an
unsigned build may be tested locally but must not be described as resolving
error 4551 or the browser download reputation warning.

## Authorization and safety rules

- Work on `codex/v1.8.2-repairs`; merge the tested result into `main` without a
  force push. Do not rewrite or delete historical branches.
- Preserve the initial dirty tree. The ignored backup at
  `.project/local/v1.8.2/preexisting/` contains the starting patches and copies.
- Preserve `BiWheel3D/` as a separate repository. Do not stage, reset, clean,
  merge, or publish it as part of this release.
- Preserve `Documents/WheelAthlete/Model`, `PC Sessions`, `Logs`, raw/derived
  athlete data, and custom install locations through upgrade/uninstall tests.
- The user authorizes source fixes, building, flashing, and readback testing of
  the currently connected green XIAO C only. Re-enumerate immediately before
  flash, require the physical USB identity to match the observed center board,
  flash only the `center` environment, and record artifact SHA-256 plus port.
- Do not flash L/R, install certificates, buy a signing service, weaken Windows
  security policy, or disable Smart App Control.
- Update `.project/STATUS.md` and `.project/HANDOFF.md` after each stage and at
  the end of every working session. Store unsanitized local evidence only under
  ignored `.project/local/v1.8.2/`.

- A local Graft graph was built for the Windows Python source at

## Stage 1 - Preserve, inventory, and establish the baseline

1. Save starting staged/unstaged binary patches and copies of untracked source
   in the ignored evidence folder. Record branch, HEAD, remotes, sub-repository
   boundary, relevant tool versions, installed application paths, registered
   uninstall entries, shortcuts, and active WheelAthlete processes.
2. Build or refresh the local Graft source graph only for maintained source.
   Exclude `release/`, `build/`, `.project/local/`, recordings, models, and
   `BiWheel3D/`.
3. Run focused baseline checks before each subsystem change. Existing failures
   are recorded separately from failures introduced by 1.8.2.

Exit gate: backup is readable, branch is correct, protected data locations are
listed, and no cleanup or release mutation has occurred.

## Stage 2 - Results browser and batch export

1. Use one in-memory `set[str]` of session IDs as the selection authority for
   date/topic cards and the flat table. Rebuilds, filtering, tab changes, and
   collapse/expand operations render from that set.
2. Present the primary hierarchy as Day -> Experiment -> Trial, newest local
   calendar day first. Day and experiment containers are collapsible; collapsing
   never changes selection.
3. Provide exactly three batch actions:
   - `Select this day`: replace the selection with every recording on that day,
     regardless of the active text/topic/trial filter;
   - `Select all recordings`: replace the selection with every session in the
     current storage root;
   - `Clear selection`: empty the selection.
4. Display the unique selected count and selected local date labels beside the
   export action. Export resolves selected IDs against the current session list,
   de-duplicates by ID, and exports each recording once.
5. Keep metadata edits, preview, delete confirmation, and existing export folder
   behavior unchanged.

Tests: day-only/all/clear selection, persistence across filters and both views,
collapse persistence, duplicate IDs, removed sessions, empty data, unavailable
dates, local midnight boundaries, and one-export-per-ID count.

Exit gate: focused Results tests pass and an offscreen GUI smoke check shows the
three actions, hierarchy, collapse behavior, and accurate selection summary.

## Stage 3 - Graceful installed-daemon lifecycle

1. Add a localhost IPC `shutdown` request. It must:
   - finalize a recording already in progress using the existing end-record path;
   - stop live preview through the existing stop path;
   - reject shutdown while recording startup is incomplete, with an actionable
     error instead of aborting the open journal;
   - acknowledge success before the daemon event loop exits.
2. Add an installer helper that targets only `WheelAthleteDaemon.exe` processes
   whose resolved executable path is within the selected installation root.
   For 1.8.2+, request graceful IPC shutdown and wait for exit. For an older
   installed daemon, query status, finalize an active recording, stop live mode,
   and terminate only the verified installed process after the graceful work.
3. Run the helper from both upgrade preparation and uninstall initialization.
   If recording finalization or process exit fails, block binary replacement or
   removal and show the exact recovery action.
4. Remove installed application binaries and shortcuts/registration using Inno
   Setup. Retain Model, PC Sessions, Logs, and user-created data directories.

Tests: idle shutdown, live shutdown, active-record finalization, startup-in-
progress rejection, unknown/foreign process protection, old-layout fallback,
custom install path, no-running-daemon case, and failed-exit blocking behavior.

Exit gate: install, launch, upgrade, uninstall, and reinstall complete with no
installed GUI/daemon process or application binary left after uninstall, while
sentinel recordings and custom models remain byte-identical.

## Stage 4 - Windows signing and reputation boundary

1. Add optional build inputs for a trusted certificate selector and RFC 3161
   timestamp URL using Windows SignTool already provided by the SDK. Do not add
   a signing dependency or store credentials in the repository.
2. When signing inputs exist, sign the GUI executable and daemon before creating
   the portable archive, then sign the installer. Verify every signature with
   `signtool verify /pa /all`; fail the release build if any requested signature
   is missing or invalid.
3. When signing inputs are absent, produce an explicitly marked local unsigned
   build and a failing `public_release_ready=false` signing report. Never upload
   that installer as the trusted public 1.8.2 asset.
4. Document separately:
   - browser/SmartScreen download reputation warning;
   - Smart App Control/Application Control error 4551 after install;
   - trusted CA-backed signing as the required distribution remedy.

Exit gate: signing automation is testable with a local test certificate, and the
release metadata truthfully reports whether public signing passed. Current
expected state is blocked until a trusted signing identity is supplied.

## Stage 5 - Portable model bundle contract and concise model UI

1. Reuse the existing `ModelSpec` and runtime adapters. Add one bundle manifest
   named `wheelathlete-model.json`; do not add a plugin framework or arbitrary
   Python execution.
2. Manifest schema v1 requires:
   - `schema_version`, stable `model_id`, short `display_name`, `model_version`;
   - supported existing `runtime_kind` and relative `artifact` path;
   - `preprocessing_id`, ordered `required_sensor_roles`, input sample rate and
     feature dimension;
   - output capability names and units;
   - experimental flag and optional short description.
3. Resolve every artifact path within the bundle directory, reject absolute or
   escaping paths, missing files, duplicate model IDs, unsupported schema/runtime,
   incompatible roles/features/sample rate, and invalid output units.
4. Scan direct child bundle directories beneath the existing Model library.
   Installed operation must not require the `BiWheel3D` checkout. Preserve legacy
   direct `.onnx`, `.pt/.pth`, and recipe `.json` loading.
5. Display concise names such as `Classical v1`, `Residual v1`, `Slalom v3`, and
   `Hybrid v1` in the selector. Show runtime, technical model name, version,
   required sensors, outputs, and experimental status in the existing details
   area/tooltips.

Tests: valid synthetic bundle without `BiWheel3D`, path traversal, missing
artifact, duplicate ID, unsupported version/runtime, incompatible input, invalid
units, concise menu text, details text, legacy import, and unchanged default.

Exit gate: a clean installed app discovers and runs a supported synthetic bundle
from the user Model folder, rejects unsafe/incompatible bundles clearly, and
keeps the classical Windows default unchanged.

## Stage 6 - XIAO C fault diagnosis, firmware repair, and flash

1. Complete the current unflashed C-only observation if the connection remains
   stable. Capture device info, sample/range/scale identity, notification/sample
   rates, sequence gaps, queue high-water/overflow, FIFO faults/dropped samples,
   transport failures, fatal host state, and STOP acknowledgement.
2. Trace the red LED and stopped-stream path across firmware sampling, FIFO,
   transport notification, BLE disconnect callback, and Windows health parsing.
   The current red condition is triggered by cumulative sample/drop evidence;
   preserve that evidence rather than clearing counters to hide the LED.
3. Add only the diagnostics needed to identify the actual fault: last disconnect
   reason, latest transport/notification error, first-fault timestamp and stable
   cumulative counters. Make the GUI `Check` state show this concrete cause.
4. Reproduce the approximately ten-minute failure before changing behavior when
   possible. Fix the shared root cause. Do not merely change red to green or
   suppress a counter.
5. Run XIAO host tests and build the `center` firmware. Record source commit/tree,
   PlatformIO environment, artifact path, size, and SHA-256.
6. Before flashing, stop active host BLE ownership, re-enumerate USB, and require
   COM20-equivalent Seeed VID/PID plus the recorded serial and BLE role C. Flash
   only the center environment, then read back BLE name/role, firmware version,
   ranges/scales, and green identity behavior.
7. Run a post-flash 30-minute C-only stress check, followed by the required
   30-minute simultaneous L/R/C acquisition when L and R are available. Save,
   reopen, and export the resulting journal; reconcile per-role produced,
   notified, received, stored, drop/replay, FIFO, and STOP counters.

Exit gate: the specific center board is flashed and identified, the original
fault is either reproduced and fixed or explicitly remains unproven, C-only and
L/R/C checks meet zero-loss expectations, and journal reopen/export preserves C.
Build/upload evidence alone is never physical acceptance.

## Stage 8 - Verification, cleanup, merge, and release

1. Run focused checks after each subsystem, then:
   - `python scripts/verify_project.py`;
   - `python scripts/run_verification.py --suite windows`;
   - `python scripts/run_verification.py --suite mobile` because Flutter source
     remains maintained in the repository;
   - XIAO host tests and center build;
   - applicable `pip audit`/dependency audit without installing or changing
     locked dependencies;
   - `python scripts/verify_project.py --staged` before every commit.
2. Build portable and installer artifacts. Test install/upgrade/uninstall/reinstall
   using a bounded disposable install directory and sentinel user data. Record
   hashes, file inventory, registration, shortcuts, launched GUI/daemon, and
   post-uninstall process/folder state.
3. Remove only enumerated regenerable project build/cache artifacts. Never use a
   blanket `git clean`; verify every resolved deletion target is within the
   intended project build/cache directory.
4. Review staged and committed diffs for private paths/data, generated packages,
   unrelated dirty work, secrets, and accidental `BiWheel3D` inclusion.
5. Commit the scoped changes on `codex/v1.8.2-repairs`, push the branch, merge
   into `main` without force, rerun the release-critical checks at the exact main
   SHA, and push main.
6. Create and publish tag/release `v1.8.2` only if the public signing gate and all
   required software gates pass. Upload Windows installer, portable ZIP,
   SHA-256 checksums, and accurate release notes; publish no mobile asset. If the
   trusted signing gate remains blocked, publish source/main changes but leave
   the GitHub binary release unpublished and record the exact blocker.

Final acceptance matrix:

| Area | Required evidence | Release effect |
|---|---|---|
| Results/models/daemon | Focused and full Windows tests pass | Blocks source merge on failure |
| Flutter maintenance | Analyzer/tests pass; no release asset | Blocks source merge on failure |
| Installer lifecycle | Install/upgrade/uninstall/reinstall and preserved sentinels | Blocks binary release |
| Trusted signing | Valid CA-backed signatures on GUI, daemon, installer | Blocks public binary release |
| XIAO C | Identified flash/readback and measured stress evidence | Report exact pass/partial state |
| Project hygiene | Normal/staged checks and private-data review pass | Blocks commit/push |

## Session handoff contract

At each stage boundary and before ending any work session:

1. update `.project/STATUS.md` with completed checks, measured values, current
   failures, branch/SHA, hardware identity, and release readiness;
2. update `.project/HANDOFF.md` with the exact next command/action, active process
   or hardware state, evidence paths, uncommitted files, and prohibitions;
3. keep detailed raw logs under `.project/local/v1.8.2/` and only sanitized,
   durable evidence under `.project/reports/`;
4. tell the user in chat immediately before starting and after completing the
   current stage, including what remains blocked.
