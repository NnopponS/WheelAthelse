============================================================
TIME SYNCHRONIZATION
============================================================

Do NOT use PC notification-arrival timestamp as the primary sample timestamp.

Keep arrival time only for diagnostics.

Port/adapt the good synchronization concepts already present in the Flutter
mobile application.

Use a PC monotonic master clock.

For each board establish a mapping:

PC_time = a * device_time + b

Use repeated round-trip synchronization measurements.

Before each recording:

- subscribe to Sync notifications
- collect multiple sync pings per board
- measure RTT
- reject high-RTT outliers
- use minimum-RTT / robust-fit observations
- estimate offset
- establish device->PC clock mapping

Then choose one future PC start time, for example:

T0 = PC monotonic time + 3 seconds

Convert this same T0 into:
- Left target device time
- Right target device time

Send scheduled START commands to both boards BEFORE T0.

Do not rely on:

send START Left now
then send START Right now

for synchronization.

Both devices must start from their own local scheduled target.

Require START_FIRED from both boards.

Store actual start timestamps.

During dual-wheel high-rate recording:
avoid unnecessary GATT control traffic.

Do not continuously send sync traffic if it demonstrably causes notification
congestion.

A preferred strategy is:

pre-record synchronization
    ->
scheduled START
    ->
STREAM ONLY
    ->
STOP
    ->
post-record synchronization

Then use pre/post clock mappings to estimate drift.

If continuous sync can be proven harmless under physical testing, it may be an
optional mode, not a requirement.

============================================================
STOP SAFETY
============================================================

STOP must be reliable.

For both wheels:

1. stop nonessential GATT traffic
2. send STOP
3. bounded retry on transient failure
4. wait for STOP_FIRED
5. allow firmware queue drain
6. receive final ACQ_HEALTH
7. compare final counts
8. finalize raw journal
9. calculate session QC
10. only then generate final session state

If STOP fails on one wheel:
- preserve the other wheel
- disconnect the failed wheel if necessary to trigger firmware failsafe stop
- mark the session degraded/invalid appropriately
- never discard diagnostics
